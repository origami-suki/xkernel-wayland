# 项目文档巡检

让下一位 Agent 能以少量、可信的上下文确定当前目标、已知事实、阻塞和下一步。文档是否需要处理，取决于它是否误导当前工作，而非文件年龄或数量。

## 范围

在用户指定或当前工作区的 XKernelGUISupport 项目中操作。项目位置不明确时只询问路径，不扫描其他项目。

默认“巡检”只读，直接在对话中报告；不创建巡检日报、不执行构建或运行测试、不修改代码、配置、镜像、Git 状态或原始证据。用户明确要求“整理/修复文档”时，在已授权范围内修正确认的问题，无需逐处请求批准；无法确认的事实保留不确定性。遵守当前对话更窄的限制。

## 渐进读取

1. 先理解适用的项目规则，再读 `docs/roadmap.md` 和它指向的当前模块/任务记录。已在当前上下文完整提供且没有变化证据的规则不必重复读取。
2. 按需读取 README 的入口、版本配置清单和对应验收项。跟随仓库现有引用；模块记录可能位于 `docs/modules/` 或 `docs/tasks/`，不因为目录不同就要求迁移。
3. 先用文件清单、标题或定向搜索定位其他材料。只有当前检查涉及的依赖、链接、决策或矛盾，才展开历史模块、日志或源码片段，不默认通读所有 Markdown 或大日志。
4. 若用户要求全仓巡检，分批扩展到各模块，区分当前说明与历史记录。报告实际覆盖范围，不把局部巡检称为全仓通过。

同时检查项目是否已把上述接手顺序写进日常 Agent 入口；本 skill 中的顺序只约束调用它的巡检，不能代替普通开发对话的项目规则。

## 检查重点

- **当前事实**：当前方案、任务状态、参数、路径和命令说明是否与用户已确定的决策、对应版本的源码和实际测试证据一致。
- **重复维护**：同一事实是否在多处重复并产生分歧；应确定一个主要维护位置，其他地方引用。不要另写一份“最新总结”制造新的副本。
- **历史边界**：已放弃方案是否仍像当前方案；“某版本测试通过”是否被误写成“当前通过”；猜测或计划是否被当作已完成事实。
- **交接可用性**：roadmap 能否定位当前模块、阻塞、下一步和证据；链接是否有效；临时文件是否挤入日常文档入口。

依据问题定向读取相应证据。用户决策确定目标与约束，源码/配置说明实现，测试记录只证明其受测输入与场景。文件较新、Git 提交更多、文档写着“已完成”均不能独立证明事实。运行命令是否成功需要真实结果；静态核对不能冒充运行验证。

版本或证据不足时标为“待验证”，说明缺少什么，不猜测新状态。旧结果仍可对原受测版本有效；不能仅因 HEAD 改变就判定历史证据无效，也不能自动延伸为当前版本通过。

## 整理时的处理原则

仅在用户已要求整理/修复时应用：

- 直接更正确认的过期说明和失效引用，合并重复事实并保留引用关系。
- 历史材料优先标明适用版本、撤回状态或降低入口优先级。确需归档/移动时保留可追溯性并更新引用，不仅因“旧”就删除。
- 原始日志、性能数据、截图和首版基线证据保持原状；失败记录和未测项不能因整理而消失。
- 不把待定计划写成已实施，不借整理改变技术路线、验收标准或版本基线。对纯文档更改做差异、链接及相关事实核对，无需为此运行整个内核或浏览器测试。

## 输出

简洁说明覆盖范围，列出会影响后续 Agent 决策的问题。每项给出文件/位置、具体矛盾、依据和最小处理建议；证据不足的问题与已确认问题分开。不为了凑报告加入纯措辞或排版建议。

若执行了整理，说明实际改动、检查结果和剩余不确定项；未执行构建/运行测试时如实说明。按需更新现有模块记录，不默认新增巡检报告文件。不自动提交或创建定时任务。
