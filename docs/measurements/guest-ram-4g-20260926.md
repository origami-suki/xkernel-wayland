# guest RAM 2 GiB → 4 GiB 对照（2026-09-26）

**结论：把 guest RAM 从 2 GiB 提到 4 GiB，对"首次正文可见"耗时没有可测收益。** 干净对照的一对是 4 GiB **84.012–85.019 秒**、2 GiB **83.005–84.011 秒**（4 GiB 反而慢约 1 秒）；此前一对（同一天、受并发分析干扰，见下）为 4 GiB 75.016–76.023 秒、2 GiB 80.021–81.028 秒。两对的符号相反、差值都远小于历史轮间波动（同一配置多次测量落在 72–93 秒）。**慢启动不是 guest 内存不足造成的，加内存不是杠杆。**

## 起因、口径与输入

- 起因：用户要求"把这个内存给大一点，调到 4G 再测试一下"。这是一次受控对照，**开发配置仍为 2 GiB / 4 vCPU**；配置变更的实际参数与原因记录在本文件及各 run 的 `metadata.json`。
- 内核 `604d846e655cd409c7c3eba8b76db821840b7a51`（含 buddy 与 CPU 计账修复），bundle `artifacts/M1-012-combined-20260926/main/bundle`，`git-dirty=false`。
- 工作盘 `work/images/chromium-m1-fcntl-unknown-v1.img`，SHA-256 `9a122bcadc8efe19100f3e43cc72d3bc77796573b3572705658e2c6e74f59941`，与本页此前测量逐字节相同；`-snapshot` 启动，四次运行前后哈希不变。
- QEMU 11.1.1、`virt,gic-version=3`、cortex-a76、`tcg,thread=multi`、4 vCPU、virtio-blk/rng/gpu/keyboard/mouse、无网卡；唯一变量为 `-m 2g` / `-m 4g`。
- 浏览器参数与原测量相同（原生 Wayland、no-sandbox、`--ipc-connection-timeout=120`、原始 `file:///opt/ict-testpages/index.html`），观测脚本 `tests/chromium/measure-first-frame.sh`，宿主每秒 QEMU monitor `screendump`。
- 计时口径与 [first-frame-1s](first-frame-1s-20260925.md) 一致：零点为宿主收到启动前标记；区间为"上一张尚无内容截图"的采集开始到"第一张内容截图"的采集结束；内容帧 SHA-256 必须等于不可变 first-runnable 的 `5954354a033f30af4fa4861a5a4616b6a78bb34b2d9d72497fa3202fab6ce287`。该口径用 `artifacts/m5-mem-20260926/first-frame-interval.py` 复核，可精确重现历史 78.004–79.027 秒。

## 宿主观测（本次补充采集的字段）

此前启动测量只记录负载与进程清单，没有记录宿主内存/swap 与 QEMU 自身的 CPU、驻留。本轮用 `artifacts/m5-mem-20260926/sample-host.sh` 每 5 秒采样一次：

- **QEMU 在启动阶段的自身 CPU 为 3.0–3.9 核**（4 vCPU 基本跑满），正文出现、进入静默观察后降到 0.1–1.6 核。也就是说慢阶段是**真的在算**，不是空等。
- **guest 侧驻留从 0.18 GB 单调涨到约 1.85 GB，并在正文出现附近停止增长；2 GiB 与 4 GiB 两次的峰值相同（1.85 GB）。** 2 GiB 并没有被用满，给出 4 GiB 也没有被用上。
- QEMU `VmSwap` 全程 0.00 GB（干净对照；受干扰那对出现过 0.14–0.20 GB），宿主 `MemFree` 0.2–1.8 GB、未发生 guest RAM 换出。
- 宿主整机忙核 5.5–6.5（含桌面负载，未隔离）；同日 10:16 有另一路工作（`scripts/analyze_trace_cpu_budget.py` 的 trace CPU 预算分析）在运行，与本轮第一对的时间窗重叠，故重跑了干净的一对；干净对运行期间无其它重负载文件写入。

## 限制

- 每个配置只有 2 轮，**不构成正式五次性能比较**，不报告正式中位/加速比；同配置轮间波动本身就与配置差异同量级。
- 采样粒度为 1 秒，串口时延未校准；宿主带有桌面负载，未做隔离。
- 上述 guest 驻留是**宿主侧 QEMU RSS**，不是 MEM-01 规定的官方统计对象，不能当资格线结论。
- 本轮没有改内核、Chromium、Weston、运行库或页面，也没有附加 GDB/trace。

## 后续

内存不是杠杆，下一步应回答"同样的启动工作量，x-kernel 为什么多花数倍 guest CPU"：按原语/系统调用做 CPU 与等待预算（自编 C 探针 + 有界内核计时），而不是继续调容量或做随机点采样。Linux 对照轮没有记录宿主侧 QEMU CPU，**倍数尚未实测**；本次只能确认 4 GiB 相对 2 GiB 无收益，以及慢阶段 x-kernel 的 4 vCPU 基本跑满。
