# M0-002：工具链、工作镜像与可重复串口启动

- 目标：落实 ENV-01，得到真正执行于 x-kernel 的交互 shell 和可重复运行入口。
- 依赖：M0-001 输入锁定、M0-005 系统 QEMU。
- 实现状态：**已验证**。2026-09-24 在固定内核提交下连续两次进入 shell 并正常关机；另一次验证 monitor 停止。
- 证据状态：构建、完整参数、配置/Build ID、串口、monitor、镜像前后哈希与退出原因齐全；本机 `artifacts/` 需随阶段材料备份。
- 用户学习/阶段验收：待用户验收；本卡不证明 Weston/Chromium 显示通过。

## 实现与必要修正

内核仍基于 `v0.2.0`，本任务内核提交 `58cf0e11` 只让 Cargo 自动校正 `xtask/Cargo.lock` 中两个本地 path 包（`kaddr_layout`、`kernel-image-metadata`）的 `0.2.0-rc2` → `0.2.0`，匹配现有 Cargo.toml。没有修改运行逻辑、升级外部依赖或引入上游新代码。差异核验见 `artifacts/build-m0/lockfile-diff.json`。

- Rust 1.95.0 的 rust-src、llvm-tools、rustfmt、clippy 和目标原已齐全。
- 安装 `cargo-binutils 0.4.0`；README 指定的 musl.cc 工具链实际为 GCC `11.2.1 20211120`。压缩包 URL/SHA256 固定在 [toolchain.json](../../config/toolchain.json)，工具解包在 `work/toolchains/`，静态 AArch64 C 程序通过显式 `qemu-aarch64-static` smoke。
- [build_kernel.sh](../../scripts/build_kernel.sh) 使用实际 `platforms/kplat-aarch64/qemu_defconfig`，调用 `make defconfig`、`make build`，默认两路编译以适应宿主内存；保存版本、配置、ELF note、bundle 和哈希。上游技能里的旧 defconfig 路径不适用于此版本。
- [run_guest.py](../../scripts/run_guest.py) 检查 manifest/ELF GNU Build ID、ELF→raw bin 一致性，保存构建副本、脚本副本、主机信息、两个仓库提交和 dirty 状态。此版本 `existing_bundle()` 只检查 ELF 存在，不能照抄技能文档中关于 `justrun` 完整校验的承诺；本封装的校验也不冒充 dirty 源码的新鲜度证明。
- 原盘和审计盘保持不变。`xkernel-run.img` 初始哈希与原解压盘一致：`441b4504cfa7fef53f8458f28b4a80eb71f4fd08104f9f260627993fce47fe84`。运行固定 `-snapshot`，每次从相同基盘状态启动，运行前后校验基盘不变。

## 实际配置

QEMU `/usr/bin/qemu-system-aarch64` 11.1.1；`virt,gic-version=3`、`cortex-a76`、`-accel tcg,thread=multi`、`-m 2g -smp 4`。内核使用 release、warn 日志、NR_CPUS=4、PCI virtio。

设备为 `virtio-blk-pci`、`virtio-rng-pci`、`virtio-gpu-pci`、`virtio-keyboard-pci`、`virtio-mouse-pci`。NET/VSOCK 不附加：当前验证完全离线，避免端口转发、DHCP 和 vhost 权限成为无关依赖；编译配置不因此删减这些驱动。串口和 monitor 使用独立 Unix socket，`-display none -vga none -no-reboot`；monitor 可截屏但此阶段没有应用 scanout。

`make justrun ACCEL=n MEM=2g SMP=4 VSOCK=n NET=n DISK_IMG=<工作盘绝对路径> XKMAKE_ARGS=--dry-run` 的实际展开保存在 `artifacts/build-m0/make-justrun-dry-run.log`。封装与其保持 CPU/机型/块设备/RNG 一致，显式增加 TCG、GPU/输入、快照和独立日志通道；每次还比对 `/proc/<QEMU PID>/cmdline`。

## 失败与恢复记录

- 首轮 rootfs 准备错误注册临时 `xkernel-m0-aarch64` binfmt 规则，阻止宿主启动新 ELF，配置命令返回 2。用户恢复后验证该规则不存在，host shell/sudo 正常。后续不注册任何全局规则；详细现场保留于 `artifacts/build-m0/interrupted.md`、`artifacts/rootfs-m0/interrupted.md`。
- `m0-first-boot` 在锁文件尚未提交时已成功，作为探索记录保留；正式验收使用上面的干净内核构建。
- `m0-serial-01` 在重建尚未完成时被 bundle/HEAD 检查拒绝，没有启动 guest。
- `m0-serial-02/03` 在 QEMU 刚 exec 时读到空 `/proc/PID/cmdline`，封装过早拒绝。改为 monitor 已响应后采集 argv，`m0-serial-04/05` 及 monitor-stop 实测通过。失败记录原样保留，不计入“两次通过”。

## 可复现入口

已具备固定 Rust/QEMU 后，缺失的交叉工具链与 binutils 可按以下步骤准备（不覆盖已存在工作盘）：

```sh
mkdir -p work/toolchains work/images
curl -fL https://musl.cc/aarch64-linux-musl-cross.tgz -o work/toolchains/aarch64-linux-musl-cross.tgz
printf '%s\n' 'c909817856d6ceda86aa510894fa3527eac7989f0ef6e87b5721c58737a06c38  work/toolchains/aarch64-linux-musl-cross.tgz' | sha256sum -c -
tar -xzf work/toolchains/aarch64-linux-musl-cross.tgz -C work/toolchains
cargo +1.95.0 install cargo-binutils --version 0.4.0 --locked
test ! -e work/images/xkernel-run.img && xz -dc ../Assets/agentos-disk.img.xz > work/images/xkernel-run.img
scripts/build_kernel.sh
python3 scripts/run_guest.py --run-id my-m0-01
python3 scripts/run_guest.py --run-id my-m0-02
```

首次原始 Assets 校验运行 `python3 scripts/check_project.py --verify-assets`。脚本要求每个 run-id 未使用，默认 240 秒有界运行，不覆盖以前证据；超时经 monitor quit / terminate / kill 分层清理并返回失败。

## 学习实验

亲手执行一次 `python3 scripts/run_guest.py --run-id my-m0-learning`，对照该目录的 `command.sh`、`monitor.log` 和 `serial.log`，找出 CPU/RAM/设备及 Build ID。

关键调用链：`Makefile → xtask/xkmake/src/{build,qemu}.rs → QEMU → entry/src/main.rs::kernel_main → spawn_init_process → /bin/sh -c entry/src/init.sh → 登录 shell`。此盘没有 openrc，所以 init.sh 不切入镜像的 BusyBox inittab；`exit` 结束 PID1 后，main.rs 的回调同步/卸载文件系统并调用 `khal::power::power_off()`。解释为何 shell 已运行而原 kiosk/X11 会话没有自动启动，以及为何 monitor 有图像文件仍不能证明 compositor 在画图。
