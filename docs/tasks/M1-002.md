# M1-002：修复大型 PIE 与 ELF 解释器地址冲突

- 目标：使原镜像 Chromium `--version` 可执行，并将已复现的 ELF 装载缺口缩成独立语义修复与回归。
- 前置：M0-002 可重复 shell；M0-003 已提供补齐盘和首个故障证据；M1-001 已提供同 rootfs 的 Linux system 对照。
- 范围：`execve → kexec ELF loader → MmSpace/VMA` 的装载布局、ELF 头部校验与错误处理。不在这张卡加入 DRM、沙箱、Chromium 启动参数或其他内存重构。
- 状态：**已修复并回归通过；阶段验收待用户确认。** 修复只改解释器基址选择与非法 ELF 的错误传播，未改动 mmap/COW/堆栈语义。

## 首个实际故障

在内核 `58cf0e11a55e2bf94690ecb6684df89654000e6b`、Build ID `d3900524f685cdf2b1d956b2f3a19c43a868db04859296f345ce59b94dcbb86f`、AArch64/TCG/2 GiB/4 vCPU 下执行：

```sh
/usr/lib/chromium/chromium --version
```

串口立即出现：

```text
panicked at mm/memspace/src/vma.rs:961:9:
assertion failed: self.try_insert(area).is_ok()
```

两次独立证据：

- `artifacts/runs/m0-wayland-probes/`：补齐 Wayland 工作盘，BusyBox/musl/Weston/seatd 探测已通过，执行 Chromium 时 panic。
- `artifacts/runs/m0-chromium-original-rootfs/`：原始 rootfs 工作副本，无 Weston 增量，单独执行相同命令重现相同回溯。

两次 QEMU 自身都返回 0，但缺少 guest 成功 marker，runner 正确返回 1；不能只凭模拟器退出码宣称通过。基盘哈希前后不变。`symbolized.log` 使用相同构建的调试 ELF 生成。

## 根因

符号化调用链（路径相对 `sources/x-kernel`）：

```text
core/ksyscall/src/task/execve.rs:83
→ process/kexec/src/loader.rs:448 (装载解释器的闭包)
→ process/kexec/src/loader.rs:276 (map_elf)
→ mm/memspace/src/aspace.rs:1072 (map_runtime_vma)
→ mm/memspace/src/vma.rs:961 (insert)
```

`commit_prepared_binprm` 把解释器固定映射在常数 `USER_INTERP_BASE = 0x0400_0000`，没有检查该区间是否已被主映像占用：

| 映像 | 主程序 PT_LOAD 页对齐区间 | 与 `0x0400_0000` 的关系 |
| --- | --- | --- |
| Chromium 142（4 个 PT_LOAD） | `[0x1000, 0xe016000)`，其中 RX 段 `[0x1a2f000, 0xd3df000)` | 落在 RX 段内部 |
| 最小 80 MiB BSS PIE（本卡用例） | `[0x1000, 0x5003000)`，RW 段 `[0x10000, 0x5003000)` | 落在 RW 段内部 |
| musl 解释器自身 | `[0x0400_0000, 0x040b_4000)` | 冲突区间 |

解释器是 `ET_DYN`，其基址是内核的放置决策而非 ELF 常数；`USER_INTERP_BASE` 只是注释中的“提示”。固定使用它，任何主映像 PT_LOAD 覆盖该地址时都会命中 `VmAreaSet::insert` 的非重叠断言，把一次本应返回 errno 的装载失败升级为内核 panic。

同一路径还有三处“非法 ELF 输入触发内核断言”，与本次缺口同类，一并纳入本卡（都属于“装载失败必须返回错误，不能 panic”）：

| 位置 | 触发输入 | 原行为 |
| --- | --- | --- |
| `loader.rs` `interp_path` 短读断言 | PT_INTERP `p_filesz` 大于文件可读长度 | `assert_eq!` panic |
| `loader.rs` `map_elf` 页偏移断言 | PT_LOAD 的 `p_vaddr` 与 `p_offset` 低 12 位不一致 | `assert_eq!` panic |
| `kernel_elf_parser` `ph_range` 溢出 | `e_phoff` 极大导致 `ph_offset + size` 回绕 | 越界切片 panic |
| `kernel_elf_parser` `build` 零 `e_phentsize` | `e_phentsize = 0` | `chunks_exact(0)` panic |

已排除项：未进入 Chromium 图形后端、Wayland socket 或浏览器沙箱阶段；不依赖 Weston 增量；不是缺少 Chromium ELF 或静态 DT_NEEDED 库。

## 修复

内核分支 `task/M1-002-elf-layout`，改动两个 crate：

1. **解释器基址动态选择**（`process/kexec/src/loader.rs`）。新增 `LoadSegment` / `load_segments` / `load_range_for_segments` 计算映像 PT_LOAD 的精确占用区间（与 `map_elf` 相同的 4 KiB 页取整），`select_interpreter_base` 用 `MmSpace::find_free_area` 在 `[USER_INTERP_BASE, USER_HEAP_BASE)` 内取第一个可容纳的基址，取整到解释器首段 `p_align`。堆与 brk 的固定位置不变。
2. **非法输入返回错误**（同上 + `boot/kernel_elf_parser/src/info.rs`）。四处断言改为返回 `KError`：PT_INTERP 短读 → `InvalidInput`(EINVAL)，PT_LOAD 页偏移不一致 → `InvalidExecutable`(ENOEXEC)，`ph_range` 溢出与零 `e_phentsize` → `InvalidExecutable`。`ph_range` 签名由 `Range<u64>` 改为 `Result<Range<u64>, &'static str>`。

没有吞掉 `try_insert` 失败，也没有为绕过某个具体浏览器大小而单纯平移常数：占用区间由 PT_LOAD 实际页范围计算，Chromium 与 80 MiB BSS 用例都通过同一路径解决。

## 顺带修复：串口脚本注入的丢字节

`scripts/run_guest.py` 原先在收到 `__XK_READY__` 标记后立即把整段脚本写入串口。该标记行本身还在被回显、shell 提示符也还在输出，主机字节与客体输出交错后会被 PL011 输入路径丢弃（实测出现 `printf'\n%s%s%d\n''__XK_DONE_'…` 这类缺空格的行，以及 `/bin/sh: can't create : nonexistent directory`）。同一内核同一脚本因此时通过时不通过，会污染后续所有需要串口脚本的验收。

修复：`phase` 增加 `await-prompt`，必须等到标记之后的那个提示符出现才发送脚本；发送前不再有未完成的客体输出。`m1-paced3-malformed-{1,2,3}` 为修复后三次连续复跑，均 PASS。逐字符节流方案（每字符 1 ms）试过并放弃，实测会与客体回显互相截断。

## 剩余问题

- `bad-filesz`（PT_LOAD `p_filesz` 被改成 1 而 `p_memsz` 不变）在 x-kernel 上子进程 exit 0，Linux 上 SIGSEGV。x-kernel 未把 `p_filesz` 作为文件数据边界约束后续读取，属于 filemap/COW 语义差异，不在本卡范围，未修。已作为独立候选记录，不用它凑数或标记为已修复。
- 解释器搜索窗口固定为 `[USER_INTERP_BASE, USER_HEAP_BASE)`，即 0x0400_0000–0x4000_0000。主映像 PT_LOAD 占用该窗口时返回 `ENOMEM`（不再 panic），但不会回退到堆以上区域。当前 Chromium 与全部用例都留有充足空间；若将来出现更大映像再按实测扩展，不提前引入复杂放置策略。
- `bad-interp-short` 的错误码是 EINVAL 而非 Linux 的 EIO。x-kernel 的 `interp_path` 对解释器文本/短读统一返回 `InvalidInput`，改动它会牵动解释器文本解析的错误语义，未在本卡扩大范围。
- 本轮只验证 `--version`（进程能装载并执行）。可见窗口与原 `index.html` 显示仍属 M3-001，未因本卡通过而提升。

以下实验保留为备用材料，**2026-09-24 用户明确决定本轮不执行**。这不是「待做」或「遗漏」，本卡的实现与证据结论不依赖它；将来想补时按此执行即可。

在 host 执行 `readelf -lW work/rootfs-audit/chromium.elf`，按 4096 字节向下/向上对齐 PT_LOAD 起止地址，再加源码实际使用的装载偏移。把 `0x04000000` 标到这些区间中，解释：应用本身尚未运行，ELF 解释器也需要占用同一个进程地址空间，因此 loader 的地址选择错误会先于任何 Wayland 调用失败。

再看修复后的差异：`select_interpreter_base` 用 `MmSpace::find_free_area` 而不是常数，并用 `load_range_for_segments` 计算解释器自身要占多少页。把 80 MiB BSS 用例的 `p_memsz` 调大或调小，观察解释器基址在什么条件下离开 `0x04000000`，以及窗口耗尽时返回的是 `ENOMEM` 而不是 panic。动态变体需要以 `-DBSS_BYTES=` 重编译 fixture 并重新注入镜像，目前没有现成脚本。
