# M1-002：修复大型 PIE 与 ELF 解释器地址冲突

- 目标：使原镜像 Chromium `--version` 可执行，并将已复现的 ELF 映射缺口缩成独立语义修复与回归。
- 前置：M0-002 可重复 shell；M0-003 已提供补齐盘和首个故障证据。修复前需要 Linux 行为对照和最小 ELF 用例；与 compositor/STREAM fd 任务可并行。
- 范围：`execve → kexec ELF loader → MmSpace/VMA` 的装载布局与错误处理。不在这张卡加入 DRM、沙箱、Chromium 启动参数或其他内存重构。
- 状态：**已复现并初步定位，尚未实现修复**。不把 M0 的构建/补包成功当作本卡通过。

## 首个实际故障

在内核 `58cf0e11a55e2bf94690ecb6684df89654000e6b`、Build ID `d3900524f685cdf2b1d956b2f3a19c43a868db04859296f345ce59b94dcbb86f`、AArch64/TCG/2 GiB/4 vCPU 下执行：

```sh
/usr/lib/chromium/chromium --version
```

串口立即出现：

```text
panicked at mm/memspace/src/vma.rs:961:9:
assertion failed: self.try_insert(area).is_ok()
```

两次独立证据：

- `artifacts/runs/m0-wayland-probes/`：补齐 Wayland 工作盘，BusyBox/musl/Weston/seatd 探测已通过，执行 Chromium 时 panic。
- `artifacts/runs/m0-chromium-original-rootfs/`：原始 rootfs 工作副本，无 Weston 增量，单独执行相同命令重现相同回溯。

两次 QEMU 自身都返回 0，但缺少 guest 成功 marker，runner 正确返回 1；不能只凭模拟器退出码宣称通过。基盘哈希前后不变。`symbolized.log` 使用相同构建的调试 ELF 生成。

## 已定位边界与下一项验证

符号化调用链（路径相对 `sources/x-kernel`）：

```text
core/ksyscall/src/task/execve.rs:83
→ process/kexec/src/loader.rs:448 (装载解释器的闭包)
→ process/kexec/src/loader.rs:276 (map_elf)
→ mm/memspace/src/aspace.rs:1072 (map_runtime_vma)
→ mm/memspace/src/vma.rs:961 (insert)
```

静态核对显示 Chromium 自身四个 PT_LOAD 页对齐后互不重叠。AArch64 当前解释器基址固定为 `0x04000000`，而该 Chromium 的 RX 段映射范围为 `[0x01a2f000, 0x0d3df000)`；原 musl 的首段映射 `[0x04000000, 0x040a2000)` 落在其中。这与解释器装载阶段的重叠断言一致。详细 ELF/源码证据保留在 `artifacts/M0-003/chromium-elf-analysis.txt`。未采集修复后的动态对照，因此当前仍作为待验证的根因定位。

已排除项：未进入 Chromium 图形后端、Wayland socket 或浏览器沙箱阶段；不依赖 Weston 增量；不是缺少 Chromium ELF 或静态 DT_NEEDED 库。显式 QEMU user/Linux host 中同一用户态 `--version` 成功，是二进制有效性的补充证据，尚不代替 M1-001 的同 rootfs Linux system 对照。

下一项只围绕这个边界：构造带解释器且主 PT_LOAD 覆盖旧固定基址的最小 AArch64 PIE，在 Linux/x-kernel 对照；核查主程序、解释器、堆栈、brk 的完整区间选择与溢出/错误传播。不能仅吞掉 `try_insert` 失败或将未知系统调用返回成功；也不能单纯移动常数来躲过一个特定浏览器大小而没有边界回归。
