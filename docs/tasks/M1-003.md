# M1-003：前置计量定义与可信度校准

- 目标：PERF-01、MEM-01、TOOL-01；首次可运行时即保存可测数据，并明确不可测项。
- 依赖：时间线设计可在 M0 同步进行；动态校准需要 M0-002；浏览器指标需要 M3。
- 范围：低干扰采样、时间点/对象定义、进程树、内存校准和统计入口；不提前做复杂优化。
- 依据：`procfs` 的 status 无 RSS，`TaskStat` 的 rss/vsize 默认 0，`getrusage.ru_maxrss=0`。详见 [内存核查](../analysis/rootfs-and-memory.md)。

## 分段完成条件

1. **首帧前准备**：统一 run-id、完整环境与命令、串口/monitor 时间线；区分 QEMU启动、kernel ready、显示服务 ready、浏览器 launch、页面请求、renderer create/ready、实际显示首帧。记录时钟域和跨域对齐误差，DOM/截图时间不直接冒充呈现时间。
2. **校准工具**：小程序分别保留/触碰固定内存、共享映射、fork、退出，验证读数变化与回收；测量进程树包含范围、共享页重复计数/去重方式、峰值采样间隔和漏采误差。按实际需要补最小可靠计量，不把完整 smaps/PSS 框架预设为首帧前置。
3. **首次可运行数据**：立即存档代码和当次原始数据；可测指标继续采满至少 5 次，不可测项写原因。计量未齐全不能延迟 first-runnable tag，也不能把 0 计为峰值。
4. **稳定后的比较入口**：启动首帧、页面加载、renderer 创建、峰值内存四类各至少 5 次，原始样本/失败样本、中位数、min/max；同一工作量、缓存、参数和日志级别。先验证采样不会显著改变受测行为。

计量数据最少包括：run-id、两个仓库提交/dirty 状态、rootfs/页面标识、QEMU/host、完整参数、事件时间、样本/单位、失败原因、统计对象与测量工具版本。不得把 host QEMU RSS 等同 guest 浏览器峰值；官方统一主机计量脚本未提供，1.5G 的正式口径仍待核对。

若以后对首版补测，保持 tag 不变，单独标注补测环境/时间/方法；若必须修改首版代码才可测，不把修改后的版本冒充原始 tag。

## 2026-09-25：按用户要求做单次1秒首帧采样

新增主机单调时钟驱动的 `--sample-every-second`，保持默认guest标记采样的16帧限制；新模式以启动前标记为原点、每秒monitor截屏、最多181帧，延迟采样不伪造补帧。guest只启动既有会话并等待，取消重复进程枚举；内核和浏览器功能不变。

本次151张原图将原始页面正文首次可见时刻约束在78.004–79.027秒（约78–79秒）；边界两帧已目视确认，内容帧hash与first-runnable相同。18项host测试、脚本生成/语法和Python编译检查通过。详情、命令、误差口径与原始证据见[测量记录](../measurements/first-frame-1s-20260925.md)。

这是单次粗测，只回答本次页面出现区间；未做五次正式性能比较，未测IPC握手完成点和可信峰值内存。原有待校准项不因此标为完成。

## 2026-09-26：复用已有 trace 的启动 CPU 预算（P3）

按用户要求，只用已归档的两条 Chromium startup trace 建立"CPU 花在哪"的预算：不启动 guest、不重新追踪、不改内核。新增通用入口 `scripts/analyze_trace_cpu_budget.py`（用 `thread_dur` 计 CPU，只汇总 `depth=0`；可选阶段窗口与同名函数自身 CPU）和只读比较脚本 `artifacts/M1-003-cpu-budget-20260926/build_comparison.py`。

结果：到达 `Startup.BrowserWindow.FirstPaint`，x-kernel 已计入 CPU 至少为 Linux 的 **6.75 倍**（≥95.651 s 对 14.172 s），而同窗口 4 vCPU 容量占用比例相近（28.7% 对 30.5%）——多出的墙钟主要是**多做 CPU 工作**而非同比闲等；`FirstPaint`→`NonEmptyPaint3` 阶段 x-kernel 达到 59.7% 容量占用（Linux 28.4%，CPU 17.15 倍）。完全同工作量的 3003 次资源读取：累计 CPU 6.108 s 对 0.121 s（50 倍），累计经过时间 16.024 s 对 0.132 s（121 倍）；同一阶段内跨子系统同名函数的每次调用 CPU 高 5–22 倍。追踪机制自身也慢约 22 倍（同窗口 22.2 s 对 1.0 s），扣除后仍有 5.59 倍。

限制与偏差：x-kernel 浏览器事件比进程起始晚 46.279 s（Linux 1.7 s），因此上述 x-kernel 数字是**下界**，且该 46 秒本轮方法覆盖不到；整轮"CPU 大于墙钟"的不可能值合计约占总量的 1.3%，短片段仍不可单条引用；两侧各一次、未交错执行，宿主内存/swap 状态当次未记录，不能作为性能成绩或补丁收益。三条相关运行的输入盘 sha256 相同，用户态内容不是变量。

本轮不定位到具体内核路径，也没有产生可提交的优化。详情、口径、原始 SQL/CSV 与比较结果见[测量记录](../measurements/cpu-budget-20260926.md)。后续最小验证仍是自编 C 探针、内核侧按 syscall/路径计时，以及同一次运行内的宿主侧 CPU 采样交叉核对。
