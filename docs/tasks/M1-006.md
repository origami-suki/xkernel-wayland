# M1-006：按线程ID查询调度参数

- 来源：M3-001修复no_new_privs后，Chromium记录`pthread_getschedparam failed: 3`。
- 目标：活跃非主线程TID可被`sched_getparam`/`sched_getscheduler`正确查询，已退出/不存在TID继续ESRCH。
- 范围：先修复已复现的查询目标解析；不顺手改写调度算法、权限模型或优先级语义。setter范围须独立检查。
- 状态：已复现并定位，未修改内核，尚未验收。

## 证据

`artifacts/M3-001-diagnosis-20260925/scheduler/`包含同步探针、动态/静态二进制、编译命令/ELF/哈希和官方Abseil/musl定位材料。

- `m3-scheduler-xkernel-before-20260925`：动态（镜像musl）和静态两种各6项失败。主线程的0/TID/PID查询通过；worker的0和PID通过，但自身非主线程TID以及另一线程查询该活跃TID均ESRCH，`pthread_getschedparam`也返回3。已join和不存在TID返回ESRCH符合预期。
- `m3-scheduler-linux-20260925`：同盘/同二进制均0项失败；cond握手保证查询时worker确实存活，无sleep猜测。
- 两个runner均正常关机并保留完整bundle/命令/图像hash。x-kernel的非零退出是探针如实报告失败，Linux退出0。

路径：`core/ksyscall/src/task/sched.rs::scheduler_target`委托`kprocess::scheduler::target_task`，后者使用PID/process-leader解析；同文件的affinity路径已经单独使用`task_by_tid`。修复前须检查PID/TID命名空间与lookup契约，不直接扩大setter权限。

Chromium142 Abseil `mutex.cc:953–955`调用`pthread_getschedparam(pthread_self())`；失败打印级别是ERROR，**这条日志自身不是fatal，尚未证明它解释全部GPU launch失败**。修复后必须复跑浏览器并继续记录其他首个故障。

## 最小验收与学习

修复前/后同盘Linux对照；当前线程0、主线程TID、活跃worker TID、外部查询、退出/不存在/负TID，以及NULL用户指针的错误行为；适用内核单测、build/clippy和M1/M2回归，冻结后由独立Agent测试再提交。

学习实验：在worker中分别传0、getpid()、gettid()查询调度参数，解释Linux接口参数名pid为何经常实际选择线程，以及浏览器线程与进程的区别。
