# M1-007：Unix socket 发送者凭据与 Zygote PID 握手

- 来源：M1-006后Chromium仍报告GPU launch error_code=1002；源码追踪和同盘probe显示SO_PASSCRED是空实现。
- 状态：已修复并通过独立验收、提交及干净版本复跑；Chromium仍未显示原页，下一项见M1-009。
- 目标：先明确并实现当前Zygote路径需要的真实发送者凭据，不能伪造PID/UID/GID或让未实现选项静默成功。
- 范围：Unix socket的SO_PASSCRED状态、接收SCM_CREDENTIALS及其与SCM_RIGHTS共存的语义；不顺手扩展user namespace或完整沙箱。

## 证据与调用链

`artifacts/M3-credentials-20260925/`保存`probe.c`、`prepare.py`、编译日志、binary/hash和镜像制备。以kiosk UID/GID1000运行：socketpair→接收端开启PASSCRED→fork子进程发送4字节→父进程recvmsg并核对真实child PID/UID/GID。recvmsg与wait同步，不靠sleep猜测。

- `m3-passcred-linux-20260925`：SEQPACKET/DGRAM/STREAM三种均option=1、control=32、found=1，PID/UID/GID准确，failures=0。
- `m3-passcred-xkernel-20260925`：三种setsockopt都成功，getsockopt却返回0；4字节正文到达，control=0/found=0，failures=3，guest/runner=1。QEMU正常关机，工作盘hash不变。
- 本轮只有自动附加凭据的正常路径探针，尚不覆盖显式伪造凭据、接收缓冲截断、选项切换或所有并发/权限行为。

内核入口：`posix/net/src/opt.rs`将SO_PASSCRED映射至PassCredentials；`net/knet/src/unix/{dgram,stream}.rs`的get/set分支都是空操作；`posix/net/src/socket.rs`目前将SEQPACKET映射至DgramTransport。`UnixCredentials::new`及SO_PEERCRED的旧占位行为不能当作发送时真实凭据。

Chromium142.0.7444.59源码和hash在`artifacts/M1-006-20260925/chromium-source/manifest.json`：

1. `content/browser/child_process_launcher.h`中1002是LAUNCH_RESULT_SUCCESS枚举值，不是Linux errno。
2. `child_process_launcher_helper_linux.cc`在Zygote分支调用ForkRequest后固定写入该值；无有效handle仍可能触发GPU启动失败。
3. `content/common/zygote/zygote_communication_linux.cc::ForkRequest`创建SEQPACKET PID oracle、启用PASSCRED，经SCM_RIGHTS交给Zygote子进程，接收ping与真实PID并回传。
4. `base/posix/unix_domain_socket.cc::RecvMsgWithFlags`从SCM_CREDENTIALS读取PID；没有凭据时局部pid保留-1。这支持下一步定位方向，尚不能仅靠静态链路认定浏览器所有失败均由它引起。

`--no-sandbox --no-zygote`对照已启动独立GPU/renderer但仍黑屏且清理超时，详情见[M3-001](M3-001.md)。不把绕过Zygote当成接口修复或first-runnable。

## 原定验收步骤（实际结果见下）

1. 读取相关源码/技能，确定凭据从当前进程进入网络边界的最小所有权接口，不能让底层网络模块反向依赖进程实现。
2. 将诊断probe提升为受版本管理的回归；核对Linux关于启停选项、发送者变化、SCM_RIGHTS共存、MSG_PEEK/CTRUNC/短缓冲及显式SCM_CREDENTIALS权限的规则，再决定支持与拒绝边界。
3. 同盘修复前/后/Linux对照，加入“子进程发送、接收端不是发送端”的PID回归，保持已有STREAM生命周期/20项和M2显示测试。
4. build/clippy、相关内核单测、冻结后独立Agent实际验收；重新运行原Zygote Chromium参数，核对handle建立、GPU/renderer日志和monitor像素。失败则保留第一个新信号，不扩大猜测性修改。

学习实验：比较SO_PEERCRED与每条消息SCM_CREDENTIALS，解释为什么socketpair在fork之前创建时，连接创建者PID不能替代随后发送消息的子进程PID。

## 2026-09-25 实现与同盘对照

本轮实现、冻结后独立验收与干净版本复跑均已完成。凭据由POSIX发送入口和VFS socket写入口采集当前TGID、真实UID/GID，作为值传入transport；不使用socket创建者或接收者的身份。既有`knet`进程适配层仍在原边界，没有新增反向依赖。

- `SO_PASSCRED`保存真实状态；发送时任一端启用则记录自动凭据，接收时按本端选项决定是否输出。发送时未记录而之后启用的旧消息按Linux返回PID0/UID65534/GID65534。
- 显式`SCM_CREDENTIALS`仅允许调用者TGID及其real/effective/saved UID/GID，错误尺寸EINVAL，越权EPERM。**能力授权的任意身份代发暂不支持，包括root；不会静默接受。** SO_PEERCRED旧占位、autobind与SEQPACKET完整连接语义未改。
- 凭据先于SCM_RIGHTS输出；控制缓冲可接收部分凭据并报CTRUNC。STREAM短读保留余下字节的发送者，FD仅首次消费时交付；不同身份区间不混淆。
- ancillary改为不可变共享所有权以支持MSG_PEEK；每次peek分配独立接收FD，队列引用仍保留。DGRAM前端暂存peek消息且保持poll可读，消耗后在锁外释放。此前DGRAM忽略每次调用的DONTWAIT导致旧探针在第二次peek阻塞，本轮同时贯通该接收标志。

依据为[Linux unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html)及[v6.12 scm.c](https://github.com/torvalds/linux/blob/v6.12/net/core/scm.c)、[af_unix.c](https://github.com/torvalds/linux/blob/v6.12/net/unix/af_unix.c)。副本与hash保存在`artifacts/M1-007-20260925/references/`。
