# M1-009：proc task 目录链接数与 Zygote 单线程检查

- 状态：单线程/线程存活/退出后生命周期同盘差异已复现；未修改内核。
- 来源：M1-007凭据修复后浏览器仍黑屏；单独启动镜像中真实Chromium Zygote，Linux能回复GetSandboxStatus，x-kernel在回复前以SIGTRAP结束。
- 目标：`/proc/<pid>/task`的`st_nlink`按实际线程数动态返回`2 + live_threads`；不得固定返回3来绕过Chromium单线程检查。
- 范围：任务目录元数据及必要VFS边界，不重写整个procfs，不补造CPU或内存字段。

## 已知证据

`m3-credentials-zygote-verbose-20260925`的两个Zygote均打印初始化0个fork delegates；8张monitor帧仍黑，Chromium清理看门狗触发，guest/runner1。不能当作正常浏览器退出。

`artifacts/M1-007-20260925/zygote-status-v2/`是最小launcher：以kiosk运行，安装SEQPACKET控制FD3和DGRAM sandbox FD5，执行赛方Chromium `--type=zygote --no-sandbox`，发送真实Pickle GetSandboxStatus请求。`m3-zygote-status-v2-linux-20260925`收到4字节状态0；`m3-zygote-status-v2-xkernel-20260925`未收到回复，poll被SIGCHLD中断，wait原始status133，即SIGTRAP并带core标志，**不是exit(133)**。两run的命令、镜像与日志都保留。Linux成功后launcher请求SIGTERM清理，不能把它当成完整浏览器会话的正常退出证据。

首版launcher使用F_DUPFD保存临时FD，在x-kernel的exec前即失败；该run不属于Zygote运行证据，缺口另见M1-008。v2只改用已支持的dup2 staging，没有修改Chromium或内核。

`m3-proc-task-stat-xkernel-20260925`的BusyBox stat报告`/proc/self/task` Links=2。Chromium142官方`thread_helpers.cc::IsSingleThreadedImpl`对`fstatat(proc_fd,"self/task/",...)`的nlink先CHECK>=3，再判断是否等于3；`zygote_main_linux.cc::EnterLayerOneSandbox`会调用它，no-sandbox不跳过这项单线程检查。这条源码链和SIGTRAP支持下一步假设，**还需修复后实际回复/浏览器复跑确认因果**。

参考：[Chromium thread_helpers.cc](https://github.com/chromium/chromium/blob/142.0.7444.59/sandbox/linux/services/thread_helpers.cc)、[zygote_main_linux.cc](https://github.com/chromium/chromium/blob/142.0.7444.59/content/zygote/zygote_main_linux.cc)、[Linux v6.12 proc_task_getattr](https://github.com/torvalds/linux/blob/v6.12/fs/proc/base.c)。文件/URL/hash在M1-007 references及`artifacts/M1-009-diagnosis-20260925/`。Alpine二进制的Zygote日志行号与官方tag文件存在偏移，不能声称已匹配发行版完整patch集或抓到了SIGTRAP指令地址。

源码入口为`fs/filesystems/procfs/src/task_nodes/root.rs::ProcessTaskDir`，已有动态线程枚举/lookup。实现前检查SimpleDirOps/SimpleDir元数据接口及线程发布/退出时机，避免缓存固定nlink或在持锁状态反向读取进程表。

验收：cond同步的single/worker-alive/after-join返回3/4/3，线程TID存在性与退出时机匹配；必要坏路径/进程退出边界，build/clippy及相关单测，独立M1/M2回归；再跑真实Zygote状态探针和原浏览器入口。只要原始index首次显示就立即存档，不等待其余功能。

学习实验：保持worker在cond上存活，分别stat `/proc/self/task`与查看子目录，再join后重复；解释Chromium为何用这个Linux元数据接口检查fork前是否单线程。


## 生命周期对照

`artifacts/M1-009-diagnosis-20260925/`保存cond同步的静态C探针、pthread编译命令、制备脚本/binary/hash和Linux源码参考。`m1-proc-task-linux-20260925`依次返回3/4/3，三项全通过；`m1-proc-task-xkernel-clean-20260925`在干净M1-007内核`44751a87`依次返回2/2/2，三项全部失败。两者都是相同工作盘/二进制，无sleep猜测，QEMU正常关机，盘hash不变。guest/runner分别0和1。

首次`m1-proc-task-xkernel-20260925`在guest启动前被runner拒绝：内核已提交，而指定的旧dirty bundle仍记录父提交。该记录保留且不计作guest运行；随后先重建干净内核再用新run-id复跑，没有绕过版本校验。
