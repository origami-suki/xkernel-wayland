# M1-010：AArch64 用户态缓存同步

- 状态：已修复，通过针对性测试、内核单测及 M1/M2 回归；Chromium 原页首帧尚未通过。
- 来源：M3 的 GPU 子进程 `exit_code=132`；定向异常日志定位到真实 libgcc 缓存同步指令。
- 目标：固定 AArch64/TCG/4 vCPU 配置上，用户运行时能够读取缓存参数并同步生成的代码；保留特权指令和未定义指令的拒绝行为。
- 范围：`kcpu::aarch64::init_trap()` 的每 CPU 配置；不更换 CPU、浏览器、图形后端或沙箱选项，不把禁止指令统一当作成功。

## 复现和定位

`m3-user-exception-20260925` 在 `fc3f2348` 上仅加入临时异常日志，记录 PID/TID、PC、ESR、指令和寄存器；guest 另导出 Chromium 映射。诊断 patch、准确 ELF/BIN/debug ELF 和复跑入口保存在 `artifacts/M3-001-exception-20260925/`。此次 220 秒期限内收齐 8 张 monitor PPM，全部纯黑；未完成计划的 12 次观察，runner=1、QEMU=0，退出原因为 timeout-commands。不作为页面或正常退出证据。

首次异常为 PID/TID 85，PC `0x12060a2c`，ESR `0x6232c041`（EC `0x18`，系统寄存器陷阱），指令 `0xd53b0022`，反汇编为 `mrs x2, CTR_EL0`。映射 `0x12057000–0x12086000` 对应赛方 `/usr/lib/libgcc_s.so.1`，故障文件偏移 `0x9a2c`。实际 `__clear_cache` 导出入口位于 `0x3b80`，跳到 `0x9a20`，随后依次包含 CTR 读取、`dc cvau`、`ic ivau` 和屏障。后续 PID 251、336 在相同位置复现；每个进程的第二次记录来自信号处理后重试，不算独立根因。

临时诊断代码已经移除，最终补丁不含寄存器/用户内存日志。旧内核把该陷阱映射为 SIGILL；这解释已观察到的缓存同步崩溃，不证明所有页面问题仅由它导致。

依据：[Arm 的缓存同步说明](https://developer.arm.com/community/arm-community-blogs/b/architectures-and-processors-blog/posts/caches-self-modifying-code-implementing-clear-cache)、本地锁定 `aarch64-cpu` 的 `SCTLR_EL1.UCT/UCI` 字段定义及赛方二进制反汇编。工具差异：交叉工具链的旧 objdump 不支持该 ELF 的 `.relr.dyn`，改用内核固定 Rust 工具链的 `rust-objdump`；未修改待分析二进制。构建技能示例中的旧 defconfig 路径不存在，仍使用实际 `platforms/kplat-aarch64/qemu_defconfig`。

## 最小同盘对照

`tests/chromium/cache-sync.c` 分别构建链接赛方 `libgcc_s.so.1` 的动态版本和静态版本；以 kiosk 用户运行，逐一绑定 CPU 0–3，每个子进程用 `sched_getcpu()` 确认实际 CPU。独立测试 CTR 读取、四种按地址缓存操作、16 次 W→缓存同步→RX→执行→RW 的代码改写，以及 SCTLR_EL1、set/way 操作、未定义指令继续触发 SIGILL。每个版本共 41 项。

- `m1-cache-sync-linux-20260925`：动态/静态各 41 项全过，guest/QEMU/runner=0。
- `m1-cache-sync-before-20260925`：使用归档干净内核 `fc3f2348`，动态/静态各 24 项失败，全部是每 CPU 的 6 类缓存查询/同步正向用例；拒绝用例及亲和性检查通过，guest/runner=1、QEMU=0。
- 制备入口为 `scripts/prepare_chromium_tests.py`，同盘为 `work/images/chromium-m1-cache-sync-v2.img`；fixture manifest、编译参数、源码、二进制和哈希在 `artifacts/M1-010-20260925/fixtures-v2/`。初始 fixture 尚未运行即补上实际 CPU 检查，两个版本均保留，以上结果只指 v2。

## 修复和验证

在每 CPU `init_trap()` 设置 `SCTLR_EL1.UCT/UCI` 并执行 `ISB`，使用户运行时直接执行架构支持的操作。通过寄存器字段修改保留其他控制位；不改异常处理、页表权限或进程模型。同步 `kcpu` 的设计/安全说明。

验证命令与完整结果由 `artifacts/M1-010-20260925/run.py` 保存为各项 `.json/.log`：

- `m1-cache-sync-after-20260925`：动态/静态各 41 项全过；82 个用例名及结果与同盘 Linux 逐项相同，`probe-comparison.json` 已自动核对。
- `make defconfig`、`make build`、`make clippy` 通过。`make UNITTEST=y UNITTEST_CRATE=kcpu run ACCEL=n ...` 的固定 2 GiB/4 vCPU QEMU 单测实际执行 18 项，全过；coverage 提取与转换成功，普通/unit/debug ELF 和覆盖率均单独保存。
- `m1-cache-sync-regression-20260925`：proc task 动态/静态各 76 项、凭据两组各 118 项、调度动态/静态各 33 项、NNP 六模式、DRM 查询、rights/seals 20 项、signalfd 五模式全过；guest/QEMU/runner=0。
- `m1-cache-sync-wayland-20260925`：Weston DRM/pixman、动态 wl_shm 客户端和正常退出通过；两张 1280×800 monitor 原图变化 942,400 像素，guest/QEMU/runner=0。
- 主机 runner/frame/serial 9 项测试、shell 语法与差异空白检查通过。当前 Agent 自查已核对主/副 CPU 初始化调用、字段掩码保留、ISB、异常拒绝路径、测试失败传播和文档同步；没有宣称完成另一 Agent 的独立验收。

上述 guest 工作盘在 runner 中使用快照，前后哈希不变。所有验证固定 `/usr/bin/qemu-system-aarch64` 11.1.1、cortex-a76、TCG、2 GiB、4 vCPU；部分功能回归与构建有宿主并发，不是性能样本。

`m3-cache-sync-after-20260925` 复用 no-sandbox/Zygote/原生 Wayland 参数和原始 index：收齐 12 张 monitor 原图，1–7 全黑，8–12 与旧窗口空白图的 hash 一致；目视第 8 帧仍只有提示栏，原页内容未显示。完整导出日志没有 `GPU process exited unexpectedly: exit_code=132`，但仍有 ANGLE/Vulkan 扩展初始化失败及 GPU 进程重启；不能称 GPU 链路全部通过。清理触发 Chromium KILL 请求，220 秒 runner 超时、QEMU=0、runner=1，未正常退出、未创建 first-runnable。下一步须从剩余的 GPU/renderer 初始化和页面提交链定位最早未完成的请求；不以没有旧崩溃日志代替页面通过。

TCG 不模拟真实硬件缓存一致性问题；通过说明用户态指令许可和生成代码执行链成立，不外推异构 CPU 或硬件勘误支持。

亲手实验：使用新 run-id 运行 `python3 scripts/run_guest.py --run-id cache-sync-my-run --disk work/images/chromium-m1-cache-sync-v2.img --guest-commands tests/chromium/cache-sync.sh --timeout 120`，比较允许的 `CTR_EL0` 与仍被拒绝的 `SCTLR_EL1`，再查看动态版本 `__clear_cache` 的反汇编。用户学习与阶段验收待确认。
