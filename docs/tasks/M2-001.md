# M2-001：Weston DRM/pixman 与最小 Wayland 客户端

- 目标：在 x-kernel 中形成 Weston → DRM/KMS → virtio-gpu 的真实输出，并显示可更新的 wl_shm 客户端。
- 前置：M0-003 补齐相应 Weston 包/模块并记录版本；M0-002 已能启动；客户端前须通过 M1-004 的 stream fd/shared mmap 验收。
- 已定路线：Wayland，优先 Weston DRM 后端加 pixman 软件合成。具体启动选项按安装版本的内置帮助/文档核对，本卡不提供未经验证的 Weston 命令。

## 按层验证

1. **DRM 原语**：VERSION/UNIQUE 的空缓冲长度查询及第二次取值，资源枚举、dumb 创建/mmap、两种图案/SETCRTC/page flip；检查实际 monitor screendump 变化，不用 ioctl=0 或 flip event 代替画面。
2. **seat 与设备**：记录该 Weston 构建实际采用的 libseat/seatd 等机制、设备发现、运行用户/权限、DRM master、evdev，以及命中的 VT/KD 请求。先定位缺文件、权限、枚举或 ioctl 语义，不能把 Wayland 当作无需 VT 的保证。
3. **Weston 本身**：运行 DRM 后端、选定 pixman 合成路径，日志确认实际后端/renderer、输出模式和 DRM 设备，保存 socket/进程状态、完整参数和 screendump。若版本/构建不含所需组件，返回 M0-003 补齐，不把 headless/nested 成功当作已显示。
4. **最小客户端**：使用与包版本匹配或可复现构建的 wl_shm 客户端，确认 registry/global、共享文件 fd、pool/buffer、attach/commit、frame callback/release 和退出；连续改变内容至少两次并留两张有变化的 screendump。该步骤需要 M1-004 已通过。
5. **后续入口**：有可见客户端即可进入 M3-001；完整真实输入/10 分钟稳定性由 M2-002 承担，资源循环由 M2-003 承担，均不延迟首次 Chromium 成功存档。

Weston 软件合成与 Chromium 的 GPU/绘制路径是两个独立选择；本卡通过不能证明 Chromium 的 dma-buf、EGL/ANGLE、沙箱或多进程兼容。正式功能证据来自 guest DRM 显示面的 QEMU monitor screendump。

- 实际执行：Linux/x-kernel DRM 原语、Weston DRM/pixman、动态 wl_shm 客户端与正常退出均已验证；已完成独立验收和最终干净提交复跑。
- 实现状态：M2-001 显示最小闭环完成。查询、设备发现和 signalfd 唤醒分三个内核提交；M2-002 输入/10分钟、M2-003资源循环另行推进。
- 证据状态：已有 before/after、Linux 对照、原始 PPM 和独立测试，详见后续记录。
- 用户学习/任务验收：待完成。

## 学习实验

让最小客户端把同一块 wl_shm buffer 从一种颜色改成另一种，分别观察未提交与提交后的显示；沿“客户端映射→Unix fd→Weston 合成→DRM buffer→virtio-gpu”追踪像素，解释 Wayland socket 与显示设备承担的不同职责。

## 2026-09-25 DRM 查询与显示原语

`tests/drm/probe.c` 在同一工作盘中执行两阶段 VERSION/GET_UNIQUE 查询、短缓冲 canary、无效指针，再枚举 connector/encoder/CRTC，创建并映射两个 dumb buffer，经 ADDFB2 / SETCRTC / PAGE_FLIP 显示不同颜色并读取 flip event。

- `m2-xkernel-query-before-20260925`：5 项查询失败。VERSION 长度 0/NULL 查询错误返回 EFAULT，短缓冲发生越界复制；GET_UNIQUE 空查询错误，短缓冲被覆盖。
- `m2-linux-drm-before-20260925`：9 项查询通过，红绿两帧及事件通过。
- `m2-xkernel-drm-after-20260925`：修复后全部通过。两张 1280×800 monitor PPM 分别为 1,024,000 个 `(224,60,50)`、`(50,168,82)` 像素；原始 PPM 保留，PNG 仅供无损预览。
- 独立验收 `artifacts/M2-001-drm-independent-20260925/`：build/clippy、同一查询/绘图探针、M1 20 项与基础版本/嵌套 shell 回归通过。受测内核为 `a4927676` 加冻结 query 修复，不能写成干净提交验证。

修复按 Linux v6.12 `drivers/gpu/drm/drm_ioctl.c`：VERSION 报告完整长度、最多复制输入容量（NULL 仅查询）；GET_UNIQUE 只有完整值能容纳才复制，否则保持短缓冲不变。固定 driver identity 和未实现的 per-open master/busid 生命周期没有借此宣称通过。

输入由 `scripts/prepare_drm_tests.py` 从上一已验证工作盘 reflink 制备，编译器、源码、实际使用的 UAPI headers 和镜像 hash 随 manifest 保存。没有修改原 Assets。

## 分阶段截图与时间记录

两个 runner 复用 `scripts/frame_capture.py`，收到完整独立行 `__ICT_FRAME_<label>__` 后通过 monitor screendump 保存原始 PPM。校验 QEMU P6 尺寸、maxval=255、精确像素长度和 monitor 错误；拒绝覆盖与路径逃逸。7 条 host 测试和独立负例证明残缺 PPM 不能记为成功。helper 本身只证明文件完整，具体颜色/内容仍单独核对。

每帧记录 host monotonic 请求前后区间和 SHA256，raw monitor 响应保存在 monitor.log。这是观测时间，**不是 guest 首帧呈现时间或性能成绩**。探针的短暂保帧仅用于功能截图，不加入真实内核显示路径。

## DRM 设备发现与非 VT 会话

`m2-xkernel-no-vt-before-20260925` 证明 `SEATD_VTBOUND=0` 已让 seatd 正常激活会话，但 Weston 显式 `--drm-device=card0` 仍无法从 libudev 找到卡。该环境变量来自已核对的 seatd 0.9.1 server.c；x-kernel 使用串口控制台、没有 Linux VT，因此不伪造 tty0/KD/VT ioctl。Linux 对照保留 VTBOUND=1，差异公开记录。

`m2-xkernel-sysfs-prototype-20260925` 仅在 guest 临时验证最小发现数据，随后正式实现由 fs_boot 在启动期读取真实 `/dev/dri/card0` 字符 inode 的 rdev，导出 `/sys/devices/virtual/drm/card0` 的 `dev`/`uevent` 与 class/devchar/subsystem 链接。属性 0444；不存在卡就不导出。没有伪造 PCI 身份、热插拔或未实现的设备能力。

独立验收 `artifacts/M2-001-discovery-independent-20260925/`：build/clippy 通过；真实内核导出无需 guest mkdir；devnum 226:0、权限0444、两条索引链接同一节点；DRM 9/9 和 M1 20/20。`m2-discovery-independent-20260925` 中 Weston DRM/pixman 与 simple-shm 显示两张不同的 1280×800 monitor 图像，协议包含 2 个 pool / 2 个 buffer、frame callback 与 buffer release；客户端 SIGINT 后正常退出。Weston/seatd 保持运行后以 monitor-quit 结束此子任务，不宣称服务正常退出。

## 会话退出的独立故障

`m2-xkernel-wayland-boot-export-20260925` 已显示动态图案且 CLIENT_EXIT_OK，但等待 Weston SIGTERM 退出超时。`m2-xkernel-wayland-bounded-20260925` 保留了完整协议记录，4秒退出看门狗触发，Weston最终 exit137，runner标FAIL，没有用可见图像覆盖退出失败。

独立最小对照 `artifacts/M2-001-shutdown-diagnosis-20260925/`：Linux pending/poll/epoll 三项通过；x-kernel 已 pending 时可立刻读取，但异步发信号时 poll 到2001ms超时边界才发现就绪，epoll到2002ms返回0；之后均能读出128字节SIGTERM。子进程等待ack才退出且SIGCHLD已屏蔽，排除了意外唤醒。ksignal入队没有通知signalfd订阅者，接下来独立修复该通知路径，保持blocked信号语义。

## signalfd 就绪通知修复

进程级 pending owner 新增 arrival PollSet，process/thread 实际入队后释放信号队列锁再通知。
SignalfdAccess 订阅该源和原有 fd mask 更新源，实际 poll/read 仍按调用线程与 fd mask
检查及消费。blocked 信号继续 blocked，不制造 EINTR、不加定时轮询、不把 fd 绑到创建线程。
加入回调中重新查询 pending（验证锁已释放）、取消订阅、跨线程共享 fd 过滤及 mask 更新回归。
Cargo.lock 由构建自动更新，仅 ksignal 的依赖列表增加已有 workspace kpoll。

`m2-signalfd-after-20260925` 和同盘 Linux 五个模式通过：已 pending、异步 poll/epoll、
线程定向的异步 poll/epoll。x-kernel 异步返回约202–204ms，发送方受控延迟200ms；这是
就绪事件正确性/超时回归，不是性能成绩。`ksignal,kfd_objects,kpoll` 自测 105/105
（27/60/18），包括4项新增 signalfd 回归；测试回调首次误用 unittest assert 宏导致的
编译失败与修正后的日志分别保留。

`m2-xkernel-wayland-shutdown-after-20260925` 已确认真实会话问题随之消失：动态图案、
CLIENT_EXIT_OK、Weston caught signal15、seatd 关闭 DRM设备和客户端连接、
WAYLAND_SESSION_OK，guest/QEMU/runner 均0，PID1正常关机。最终独立测试与干净版本
复跑仍单列，不改写此前被看门狗终止或超时的失败记录。

## 验证范围和保留事项

- x-kernel 使用 seatd 非 VT 模式（SEATD_VTBOUND=0），Linux对照使用VTBOUND=1；
  两者都使用同盘 Weston14.0.2、DRM后端、pixman、kiosk-shell和显式card0。
- --continue-without-input 是已确认的实际参数；真实键鼠和连续10分钟仍属M2-002。
- sysfs仅导出启动时真实虚拟DRM adapter，不是完整PCI/sysfs或热插拔实现。
- 观察到SO_PEERCRED的uid/gid及signalfd的sender_pid仍有既存占位行为，本轮不宣称凭据隔离或完整siginfo已通过。
- DRM backing回收/100轮循环仍属M2-003；wl_buffer.release协议事件不等于所有内核内存都回收。
- 此处只有Wayland测试客户端；Chromium窗口/原始index显示及first-runnable tag仍属M3-001，不能提前建立。

可重放入口为 `tests/drm/session.sh`（会话/协议/两帧/正常退出）和
`tests/drm/regression.sh`（sysfs、DRM、M1接口、signalfd及基础版本）。
前者先收集客户端原始日志再停止服务，即使将来退出回归也尽量保留已经完成的协议证据。
Linux控制脚本只将SEATD_VTBOUND=0改为1；输入差异必须记录，不把两者写成完全相同的seat参数。

```sh
python3 scripts/prepare_drm_tests.py --output work/images/m2-new.img --evidence artifacts/m2-new-fixtures

```

再看caught signal15与seatd关闭设备。将“客户端共享文件中的像素”“Weston合成输出”
