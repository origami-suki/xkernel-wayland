# M3-001：Chromium 首帧与不可变基线

- 目标：WEB-01、BASE-01；首次在 x-kernel 内正确显示官方原始 index 时立即存档。
- 依赖：M0-003 的 Wayland 工作盘、M1-004 的 fd/shared mmap、M2-001 的 Weston DRM 输出和最小 wl_shm 客户端。浏览器试跑暴露的新阻塞转独立复现/修复任务，再继续试跑，不预设所有调用已知。
- 不作为前置：完整键鼠、10/30 分钟稳定性、JS/CSS 全部测试、所有计量字段、优化、上游合并。

## 执行和停留点

1. 复用镜像的 Chromium，优先以 `--ozone-platform=wayland` 明确启动原生 Wayland；从 M0-003 已探测的能力及内置帮助确定其余参数。设置与 Weston 一致的用户/runtime/socket，检查实际 Ozone、连接及协议证据，不能只看到命令行就判为原生 Wayland。
2. 原 X11/GLX 参数保留作镜像来源记录，不照搬。逐层记录 loader、browser/renderer、GPU/utility（按实际模式）、Wayland surface/buffer、Weston 和 DRM present；每项后端/沙箱调整有故障假设与对照，不能以单进程通过多进程验收。Weston pixman 成功不等于 Chromium 的绘制/缓冲路径已验证；若现有二进制不支持原生 Wayland，记录证据后评估兼容办法，不静默回退并谎称原生通过。
3. 指定原始测试页 URL，校验 guest 页面哈希，核对文字、CJK、表单、表格与内联 SVG；不能用镜像 kiosk 欢迎页替代。
4. **首次窗口和原页显示满足条件就停止继续完善功能，先保存**：QEMU monitor screendump、serial/显示服务/Chromium 日志、完整命令、已可测时间线、工作镜像与配置、内核和集成仓库状态。
5. 保留成功现场对应的源码，不在测试后混入下一项修改。按规则提交实际已测代码和集成指针；创建 `baseline/first-runnable`，记录两个仓库提交、镜像/工具/页面/参数及证据哈希。若当时 dirty，先完整保存，再完成原状态的验证/提交，不能把新代码的干净 tag 关联旧截图。
6. 继续采集当时可测指标，缺项如实记录。功能与稳定性进入 M4，存档 tag 不移动不覆盖。

主线优先原生 Wayland；若后续为诊断或兼容性评估引入桥接，首次真正满足既定“x-kernel 内窗口正确显示官方原页”的条件仍立即保存最早可运行版本并注明实际链路，不因原生验收未完成而推迟存档。桥接结果不关闭原生 Wayland 的能力验证。

- 实际执行：Linux同盘已显示原始index；x-kernel的no_new_privs、调度查询及发送者凭据已修复，短观察仍黑屏，干净长观察已显示浏览器顶部提示栏但正文空白；proc task链接数已修复且Zygote状态请求成功，仍无原页首帧，未创建tag。
- 实现状态：试跑中；[M1-010](M1-010.md)已修复真实GPU进程命中的libgcc缓存同步陷阱，原页仍空白，继续定位后续GPU/renderer初始化与页面提交；此前子修复见M1-005/M1-006/M1-007/M1-009。
- 证据状态：已有monitor原始PPM、协议/进程/错误日志和同盘Linux对照，见下。
- 用户阶段验收：待确认。

亲手实验：成功后打开第二个官方页面，比较 browser/renderer PID、窗口与共享内存，再关闭页面观察退出。解释浏览器窗口、renderer 和 GPU 进程各自承担什么，以及首个静态页存档为何早于完整功能验收。

## 调度查询修复后的浏览器与Zygote诊断

`m3-scheduler-after-20260925`使用M1-006冻结补丁和原`no-sandbox`观察入口：8张1280×800原始monitor PPM全部纯黑，`pthread_getschedparam failed`消失，但GPU启动仍失败9次，最终FATAL、Chromium wait=133。浏览器和Weston清理看门狗均发出强制终止请求，因此不能将Weston wait=0写成正常退出。guest/runner=1，QEMU=0；完整76,011字节serial已消费，磁盘hash不变，`display-proof.json`记录逐图结果。

`m3-no-zygote-20260925`仅在相同参数上增加`--no-zygote`。根据[Chromium142开关定义](https://github.com/chromium/chromium/blob/142.0.7444.59/content/public/common/content_switches.cc#L535-L539)，它使子进程直接fork/exec，仍为多进程并保持`--no-sandbox`。观察记录出现独立`--type=gpu-process`及`--type=renderer`；没有原先9次error_code=1002，但8张PPM仍全黑，GPU报告drmGetDevices2找不到设备，另有crashpad missing credentials。清理停在Chromium wait，150秒期限触发monitor结束，runner=1，不能称正常退出；serial记录54,775字节，停止QEMU时连接reset/EOF=false，原始日志保留。没有继续叠加GPU参数或伪造成功返回。

### 干净版本的新定位线索

`m3-proc-task-clean-final-20260925`使用内核`fc3f2348`、git-dirty=false，以及原浏览器no-sandbox/Zygote选项；只把观察改为每10秒一次、共12帧，以符合16帧采集上限。已出现明确日志`GPU process exited unexpectedly: exit_code=132`，区别于此前启动handle失败的error_code=1002。

同版本[Chromium kill_posix.cc](https://github.com/chromium/chromium/blob/142.0.7444.59/base/process/kill_posix.cc)保留waitpid原始status，已归档的`zygote_linux.cc::GetTerminationStatus`继续转发，[gpu_process_host.cc](https://github.com/chromium/chromium/blob/142.0.7444.59/content/browser/gpu/gpu_process_host.cc)记录该exit_code。按这条源码路径，132对应SIGILL(4)并带core标志，**不是正常exit(132)**；仍需对实际发行版二进制/内核信号路径抓取ELR、ESR与指令来确认触发点，不把它直接归因于GPU硬件、CPU能力或缺少某个syscall。新参考文件的URL/SHA256在`artifacts/M1-009-20260925/references/manifest.json`。

下一步优先在GPU子进程首次SIGILL时获取PID/TID、PC、异常分类和映射，必要时用最小同盘probe复现。crashpad的ptrace ENOSYS只限制错误报告，不能替代原始故障证据。


该干净run收齐12张1280×800 monitor原图：1–9帧全黑；10–12帧hash相同，已目视第10/12帧，顶部出现Chromium no-sandbox提示栏，正文是空白白色。原页的标题/CJK、四色块、表格、表单及SVG未出现，**只能判浏览器窗口壳显示，不能创建first-runnable**。原始index页面hash仍匹配，协议已记录wl_buffer attach及presentation反馈；出现GPU进程3次exit_code=132，之后ANGLE/Vulkan扩展初始化失败，再有重新初始化日志。没有把后续恢复当作前3次崩溃已修复。

逐帧像素/hash/目视说明在该run的`display-proof.json`，窗口预览为`frame-chromium-10.png`/`frame-chromium-12.png`。10秒采样只给首次非黑的观察区间，不能称页面首帧或精确启动耗时。清理看门狗再次请求终止浏览器，220秒runner期限触发monitor退出，runner1/QEMU0，exit_reason=timeout-commands；不把窗口可见当作正常退出或页面可用。

## 缓存同步陷阱定位与修复后的边界

`m3-user-exception-20260925` 的定向诊断抓到 PID/TID 85 在 `libgcc_s.so.1` 偏移 `0x9a2c` 执行 `mrs x2, CTR_EL0` 时发生系统寄存器陷阱，ESR `0x6232c041`，由内核转成 SIGILL；LR 位于 `libLLVM.so.20.1`。PID 251、336 后续同址复现。诊断源码、准确 ELF、指令和映射记录已保留，临时日志已移除。最小同盘对照与修复集中在 [M1-010](M1-010.md)。

`m3-cache-sync-after-20260925` 用 M1-010 冻结普通内核和原参数复跑，完整日志不再记录 GPU `exit_code=132`；仍有 ANGLE/Vulkan 扩展初始化失败与 GPU 重启，12 张 monitor 原图中 1–7 黑屏，8–12 为提示栏及空白正文（与此前空白图 hash 一致）。原始 index 哈希匹配；未满足 first-runnable，未创建 tag。清理看门狗请求 KILL 后等待未结束，220 秒超时由 monitor 停机；QEMU=0、runner=1。逐图哈希、协议与退出信息在 run 的 `display-proof.json` 和 `metadata.json`。

后续先区分 GPU 初始化退回、renderer 启动及页面首次提交各自的进展；SIGILL 修复后没有原页不意味着应重新扩大 CPU 特性修改，也不把 Linux 成功运行中已有的 DRM 警告单独当作新根因。
